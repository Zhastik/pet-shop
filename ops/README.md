# Сопровождение FORMA

## Запуск

Скопировать .env.example в .env только на новой установке. Указать SECRET_KEY (не менее 32 символов), DATABASE_URL и POSTGRES_PASSWORD. На существующей установке смена POSTGRES_PASSWORD в .env не меняет пароль в PostgreSQL: сначала изменить его в БД и согласованно обновить DATABASE_URL. Пароли со специальными символами в URL должны быть percent-encoded.

    docker compose up -d --build

Магазин: /shop/, документация: /docs, состояние процесса: /health/live, готовность БД и Redis: /health/ready. Проверки состояния не раскрывают строку подключения. Для публичного домена задать ALLOWED_HOSTS JSON-массивом через окружение контейнера.

Redis используется для ограничения запросов входа/регистрации (30 в минуту на IP) и отзыва сессий. При его недоступности авторизация с сессией отвечает 503. Redis сохраняет данные в отдельном томе через AOF. Не очищать его при обычных обновлениях. За reverse proxy корректно настроить доверенные proxy headers, иначе ограничение может учитывать общий адрес прокси.

SEED_CATALOG=true добавляет отсутствующие демо-модели. Для рабочего каталога можно отключить. Миграции и демо-каталог запускает отдельный одноразовый сервис migrate. Web стартует только после его успешного завершения. При ошибке миграции проверить `docker compose logs migrate`.

## Диагностика

Логи в stdout: JSON, request_id, метод, шаблон маршрута, статус, длительность. Заголовок X-Request-ID связывает ответ и логи. SQL-параметры скрыты. В ответе сохранено поле detail для совместимости фронтенда, добавлены code и request_id.

Метрики: /metrics/. Они содержат процессные счётчики запросов и гистограммы задержки. Текущая конфигурация рассчитана на один web-процесс. Для нескольких процессов нужна отдельная multiprocess-конфигурация Prometheus client.

    docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d

Prometheus доступен только локально на порту 9090. Панели Grafana и доставка оповещений требуют отдельной настройки. Для Sentry передать SENTRY_DSN через окружение web; персональные данные по умолчанию не отправляются. Публичный reverse proxy должен закрывать внешний доступ к /metrics/.

## Сессии и API

После обновления рекомендуется войти заново. Новые токены содержат sid. Обновление через /users/refresh-token или /users/access-token возвращает новую пару токенов; клиент должен сохранить оба. Повторное использование старого refresh отзывает всю сессию. POST /users/logout отзывает текущую сессию. Токены без sid не принимаются; после обновления необходимо войти заново.

Для checkout клиент передаёт Idempotency-Key. Один ключ предназначен для одной попытки оформления, при сетевом повторе его сохраняют. Уникальность действует внутри аккаунта. Повтор возвращает ранее созданный заказ. Покупки сериализуют остатки в порядке ID товаров. Изменения корзины и checkout одного пользователя используют одну блокировку пользователя.

Категории изменяет только admin; публичная регистрация администратора запрещена. Подготовка первого администратора производится оператором БД. Значимые изменения заказов, товаров и отзывов записываются в audit_events в той же транзакции. Публичного API изменения аудита нет.

## Проверки

    pip install -r requirements.txt -r requirements-dev.txt
    ruff check app tests
    mypy
    pytest
    bandit -r app -ll
    pip-audit -r requirements.txt

Mypy пока проверяет конфигурацию и middleware; покрытие типами расширять постепенно. Интеграционный тест включается RUN_DB_TESTS=1, требует отдельную PostgreSQL и доступный Redis. DATABASE_URL обязательно должен указывать на тестовую БД: тест создаёт собственные данные и сохраняет их для диагностики. CI создаёт временную БД, применяет всю цепочку миграций, проверяет конкурентную покупку последнего товара, идемпотентность и отзывы. Ruff не изменяет код в CI. Проверки зависимостей и секретов блокируют сборку при обнаружении проблем.

## Резервные копии

    python ops/backup.py backups/store.dump

Проверять восстановление в отдельной БД:

    docker compose exec db createdb -U ecommerce_user restore_check
    docker compose exec -T db pg_restore -U ecommerce_user -d restore_check --exit-on-error < backups/store.dump

Команду с перенаправлением бинарного файла выполнять в shell с поддержкой бинарного stdin (например bash), не в Windows PowerShell 5.1. Копии БД и media хранить вне Docker-хоста; автоматическое расписание и срок хранения задаются на сервере. Не удалять рабочий том для проверки восстановления.

## Дальнейшая эксплуатация

HTTPS, ограничения размера запросов и тайм-ауты задавать на reverse proxy. Нагрузочные пороги, оповещения, срок хранения аудита и резервных копий определять по требованиям развёртывания. OpenTelemetry, очередь задач и кэш не подключены: сейчас нет внешних распределённых операций, для которых они требуются.

## Результат аудита зависимостей

Первоначальный аудит обнаружил известные уязвимости в исходных зависимостях. Прямые зависимости выделены в requirements.in, лишние CLI-пакеты удалены, версии согласованно обновлены и зафиксированы в requirements.txt. Повторный pip-audit после обновления не обнаружил известных уязвимостей. Это результат проверки на момент обновления, поэтому аудит продолжает выполняться в CI.

.env ранее отслеживался Git. Он исключён из индекса, локальный файл сохранён. Секреты из уже опубликованной истории требуют ротации; удаление файла из нового коммита не удаляет старые версии.


## Обновление зависимостей

requirements.in содержит прямые зависимости. requirements.txt — разрешённые и проверенные версии, полученные pip-compile для Python 3.12. В окружении разработки установить requirements-dev.txt, затем выполнить `pip-compile --upgrade --strip-extras requirements.in`, повторить pytest и pip-audit. Uvicorn используется без платформенных extras, чтобы список можно было устанавливать и в Windows. Последняя проверка после обновления: 12 тестов прошли, pip-audit не обнаружил известных уязвимостей. Старый отчёт выше сохранён как история причины обновления.

Интеграционные тесты принудительно требуют имя БД, заканчивающееся на _test. Время подключения и команд Redis ограничено двумя секундами; отзыв и использование refresh выполняются одной Lua-операцией.

## Смотри: сотрудники и характеристики

Публичная регистрация создаёт только buyer. Роль staff назначается администратором в личном кабинете → «Сотрудники» либо PATCH /users/{id}/role. Старые самостоятельно зарегистрированные seller при миграции становятся buyer и требуют подтверждения администратором. Сотрудник может изменять товары магазина; личное владение каталогом больше не ограничивает эти операции. seller_id пока сохранён как техническое поле совместимости, а не роль.

Создать первого администратора на своём компьютере:

    docker compose exec web python -m app.create_admin

Команда интерактивно запросит email и пароль, секреты не передаются в аргументах и не публикуются. Она не изменяет существующий аккаунт. После входа администратор может найти зарегистрированного пользователя и назначить или снять роль сотрудника. Повышение до admin через публичный API запрещено.

В multipart создания/обновления товара поле specifications принимает JSON: brand, model, sku, purpose, frame_shape, frame_material, frame_color, lens_material, lens_color, lens_width_mm, bridge_width_mm, temple_length_mm, weight_g, polarized, uv_protection, prescription_ready, included, care. Неизвестные значения оставлять null. Демонстрационный каталог отмечен demo=true: данные придуманы для интерфейса и не являются подтверждёнными свойствами реальных товаров. Остатки и цены существующего каталога не перезаписываются.

Личный кабинет /shop/#account показывает данные текущего пользователя и историю заказов с пагинацией, позициями, количеством, ценами на момент оформления и статусом. Статусы не предполагают добавления доставки или оплаты.
